## 1. 一句话定位

> 本工作台是 **数据中台「元数据 / 血缘 / 变更闸门」能力的前身**，同时承担当前 **数据库重构专项** 的过程作业；成熟后并入中台，而不是长期平行建设一套「伪中台」。

它不是：业务办理系统、全息综合展示、生产供数平台。  
它面向：数据 / 研发 / 治理专业人员。

---

## 2. 工作台理念（现在实际在守什么）

在「缺设计文档、只有金仓 DMP + 源代码」的约束下，先解决：

> **如何把遗留库摸清，把字段级引用做成可验收事实，从而安全地评估「能不能改」。**

三层理念：

| 层 | 含义 |
|---|---|
| 作业理念 | P0–P6 / 29 表流水线：结构还原 → 访问归集 → 字段引用 → 问题与风险 → 生产确认 |
| 事实理念 | **表 15（字段 × 接口 × 操作）** 为脊柱；库表字段、系统模块接口均由此派生 |
| 证据理念 | 每条结论保留 **证据来源 / 结论等级 / 适用范围**，支撑「敢改 / 不敢改」 |

交互只守两个问题（与中台血缘最小可用面一致）：

1. **字段被谁用** — 影响分析  
2. **接口用了什么** — 触达面  

与周边系统边界：

```text
业务系统（规划 / 执行 / 评估 / …）
        ↓ 接入与交换（中台期）
数据中台（目录 · 标准 · 质量 · 血缘 · 服务 · …）
        ↑ 本工作台先孵化「目录 + 血缘 + 闸门」
        ↓ 数据服务
全息平台及其它应用（面向业务用户）
```

---

## 3. 为什么可以作为中台前身

中台要立住，通常先缺三块：

| 中台能力 | 工作台已有种子 |
|---|---|
| 资源目录（有什么） | 对象总览、字段主表、过程表清单 |
| 血缘（谁在用） | 表 15 + 引用树 / 触达树 |
| 变更影响（能不能改） | 引用面统计、重构风险评估、闸门叙事 |

P0–P6 过程页是 **「从混乱到可治理」的过渡作业面**：中台成熟后可弱化，前身阶段必须保留。

**不要**把工作台做成完整中台；稳妥目标是：

> 中台内 **元数据 / 血缘 / 变更闸门** 模块的前身 + 重构专项作业系统。  
> 接入、标准、质量、主数据、服务、交换按中台路线图后挂。

## 4. 现状判断：还缺什么

### 4.1 前身阶段必须补齐（否则只是演示）

| # | 缺口 | 说明 |
|---|---|---|
| 1 | **真实数据管道** | DMP 导入、源码扫描、回填表 15、任务可重跑；当前 Make UI 仍以演示 `facts` 为主 |
| 2 | **证据确认闭环** | 「解析 / 上传 / 推导 / 逐条确认」要落库：谁、何时、版本、可回滚 |
| 3 | **资产身份稳定** | schema.table.field / 系统.模块.接口 稳定 UID + 变更历史 + 生产差异对照 |
| 4 | **前后端统一真相** | 过程表、引用树、风险表走 API；避免 UI 演示数据与 SQLite 两套真相 |

### 4.2 迈向中台时再长的能力（现可不做，须留扩展口）

| 中台能力 | 工作台现状 | 演进建议 |
|---|---|---|
| 资源目录 | 过程表 / 字段清单雏形 | 演进为可检索资产目录服务 |
| 数据标准 / 字典 | 有表位（09 / 20） | 从盘点升为标准发布 |
| 主数据 | 几乎无 | 另模块建设；工作台只挂引用关系 |
| 质量 | 无规则引擎 | 后置；先用差异 / 孤儿 / 隐式关联作弱信号 |
| 血缘 | 字段↔接口 强 | 再补作业级（ETL/任务），再谈主题血缘 |
| 数据服务 | 无 | 中台期 API / 指标服务 |
| 交换 / 同步 | 无 | 中台接入层 |
| 权限 / 审计 | 刻意延后 | 并入中台前必须补 |

### 4.3 产品上要避开的坑

- 不做第二个全息（综合展示不是主战场）  
- 不做纯 ETL 平台（接入是手段，脊柱仍是元数据与字段血缘）  
- 不过早堆「中台十大模块」（稀释当前「重构可验收」刚需）

## 5. 演进路线

```text
阶段 1  重构工作台（前身）     ← 当前
        DMP+源码 → 29表过程 → 字段血缘双问 → 变更风险闸门
        验收：给定字段能答清谁用、改了影响谁，且证据可追溯

阶段 2  中台「元数据/血缘」MVP
        资产目录 API + 血缘查询 API + 证据版本 + 影响分析接口
        工作台 UI 可降级为中台内一个应用

阶段 3  中台扩展
        标准 / 质量 / 主数据 / 服务 / 交换
        工作台过程能力保留为「专项治理作业」，不再是唯一入口
```

验收分水岭：

- **前身验收**：人在工作台里能完成摸底与影响分析。  
- **中台验收**：其它系统能通过服务查目录与血缘，而不必打开本工作台。

## 7. 阶段 2 预留接口（先占位，后实现）

便于前身模型不推倒重来，建议后端尽早按「可服务化」形状设计：

| 能力 | 建议形态 | 说明 |
|---|---|---|
| 资产检索 | `GET /api/catalog/assets` | 库/表/字段目录 |
| 字段血缘 | `GET /api/lineage/field` | 已有雏形，固化契约 |
| 入口血缘 | `GET /api/lineage/entry` | 接口触达面 |
| 影响分析 | `GET /api/impact` | 变更影响（闸门输入） |
| 证据批次 | `GET/POST /api/evidence/...` | 确认与版本 |
| 导出 | `GET /api/export/metadata` | 供中台导入的 JSON/包 |

阶段 2 验收标准：中台或其它系统只调 API，即可复用本工作台沉淀的目录与血缘，而不依赖页面。

---

## 8. 结论

- **理念正确**：逆向摸底 + 字段级引用事实 + 重构闸门 = 中台元数据/血缘前身。  
- **最大缺口**：真实接入与落库、证据确认闭环、前后端统一真相——不是再堆页面。  
- **扩展原则**：先把「目录 + 血缘 + 影响」做成可被中台吸收的服务；标准 / 质量 / 服务 / 交换后挂。

阶段 1 清单勾完，即可启动「并入中台元数据/血缘模块」的正式设计。
